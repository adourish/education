# Integration, cost, monitoring, analytics, resilience — question review

Reviewed 75 questions across six files. Found 6 problems.

## Out of date

### gh-267 (integration.md)
**Stated answer:** D. Create an Amazon Kinesis Data Firehose delivery stream to store the data in Amazon S3. Create an Amazon Kinesis Data Analytics application to analyze the data.
**Now:** The architecture is still the right one — Firehose can encrypt on the way through and convert records to Apache Parquet before landing them in S3, which is the "near-real time" and "centralized Parquet" part of the requirement. Only the second service name is stale: Amazon Kinesis Data Analytics for Apache Flink was renamed **Amazon Managed Service for Apache Flink** in August 2023, and the SQL-based flavour of Kinesis Data Analytics has been retired. A candidate sitting the current exam will see the new name on the answer options, so this question should say "Amazon Managed Service for Apache Flink".

### gh-292 (integration.md)
**Stated answer:** A (Kinesis Data Streams → Amazon Kinesis Data Analytics to transform → Firehose to S3 → Athena) and B (Amazon MSK → AWS Glue → S3 → Athena).
**Now:** Both answer choices are still correct, so a candidate would score this right. The wording carries the same stale name as gh-267: "Amazon Kinesis Data Analytics" is now "Amazon Managed Service for Apache Flink" (renamed August 2023). Worth updating for consistency with the rest of the bank, and it is no longer accurate to describe the SQL variant of that service as available.

### gh-201 (integration.md)
**Stated answer:** B. Build an Amazon Pinpoint journey. Configure Amazon Pinpoint to send events to an Amazon Kinesis data stream for analysis and archiving.
**Now:** This was the accepted answer when the question was written, and streaming Pinpoint events into Kinesis so they can be retained and analysed is still the right *shape* of solution. But the product has been split and renamed: the SMS, voice and push channels — including the two-way SMS and reply capture that this question depends on — moved to **AWS End User Messaging** (announced late 2024), and AWS has published an end-of-support date for the Amazon Pinpoint orchestration features that "journeys" belongs to. Anyone building this today would use AWS End User Messaging SMS with two-way messaging enabled and an event destination to Kinesis Data Streams. Treat the answer as directionally right but the service naming as superseded.

## Explanation problems

### gh-7 (integration.md)
**Issue:** The answer (publish to an SNS topic with multiple SQS queue subscriptions, one per consumer) is correct, but the second half of the explanation states throughput limits that do not exist for the queue type being used. It claims "an SQS queue can handle a maximum of 3,000 messages per second... AWS can increase the message throughput... up to a maximum of 10,000 messages per second." Standard SQS queues have **no published throughput ceiling** — they support a nearly unlimited number of messages and transactions per second with no quota increase needed, which is precisely why this answer survives the 100,000-messages-per-second spike in the question. The 300-per-second and 3,000-per-second figures belong to **FIFO** queues (300 per API action, 3,000 when sending in batches of 10), and high-throughput mode for FIFO raises them far beyond 10,000. The "contact AWS Support for increments of 300" story is not current AWS behaviour for either queue type. The final paragraph, which says the API can accept messages faster than the queue can hold them, is also meaningless — accepted messages are in the queue by definition.

### gh-50 (monitoring.md)
**Issue:** The answer (Systems Manager Run Command) is correct — it is the quickest way to push an ad hoc patch command to 1,000 instances at once, which is what the question asks for. The reasoning used to reject the other options is wrong on two counts. First, it says "Patch Manager is not designed to apply third-party software patches." Patch Manager **does** patch third-party applications (application patching on Windows, and OS-level package patching from configured repositories on Linux). Second, it says maintenance windows "are not designed to apply patches to third-party software" — a maintenance window is just a schedule, it has no opinion about what it runs. The real reason to reject both is timing: the question says "as quickly as possible," and Patch Manager with a maintenance window waits for the next scheduled window, whereas Run Command executes immediately. The explanation should say that instead of inventing capability limits.

### gh-585 (resilience.md)
**Issue:** The answer (purchase a Capacity Reservation in the failover Region) is correct, but the explanation misstates how On-Demand Capacity Reservations work: "Capacity Reservations offer flexibility, allowing you to launch different instance types and sizes within the reserved capacity." An On-Demand Capacity Reservation is pinned to a **specific instance type, platform/OS, tenancy and single Availability Zone** — you cannot launch a different instance type or size against it, and it does not span AZs. (Instance-type flexibility only appears if you use a Capacity Reservation Fleet, which is a different feature and is not what the answer says.) This matters for the exam, because the flexibility the explanation describes is the property of a **Compute Savings Plan**, which is a billing discount and reserves no capacity at all — exactly the distinction this question is testing.

### gh-454 (unclassified.md)
**Issue:** The answer (Workload Discovery on AWS) is correct, but the explanation invents a relationship between two products: "AWS has a service called AWS Well-Architected Tool, which includes Workload Discovery." It does not. **Workload Discovery on AWS** is a standalone AWS Solutions Library implementation that you deploy into your own account from a CloudFormation template; it inventories resources across accounts and Regions and draws architecture diagrams. The **AWS Well-Architected Tool** is a separate service for running workload reviews against the Well-Architected pillars — it produces improvement plans and risk findings, not resource inventories or architecture diagrams, and it contains nothing called "Workload Discovery." The explanation also credits it with "best practice recommendations," which is the Well-Architected Tool's job, not Workload Discovery's.

Checked 75 questions: no answers are outright wrong, 3 are stale on service naming (two Kinesis Data Analytics references and one Amazon Pinpoint), and 4 explanations state facts that are not true — the SQS throughput limits in gh-7, the Patch Manager capability claims in gh-50, the Capacity Reservation flexibility claim in gh-585, and the invented Well-Architected link in gh-454. Overall these six sets are the strongest reviewed so far: every answer letter is defensible against current AWS behaviour and the qualifiers ("MOST cost-effective", "LEAST operational overhead") are respected, so the work needed is editorial — refresh three service names and rewrite four explanations — rather than re-answering anything.
